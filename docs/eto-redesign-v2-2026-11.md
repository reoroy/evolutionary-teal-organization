# dsh-eto 改造方案 v2

> 基线 `b3e58b8`（CI success）。本方案的每条判断都标了证据来源；能在本机复跑的都写了命令。
> 配套 demo：`docs/demo/eto-ledger.html`（单文件，双击打开）。
> **本轮只出方案与 demo，未改 `lib/` 与 `eto/` 一行实现代码。**

---

## 三句话摘要

1. **它现在没人用，不是因为能力弱，是因为它站在一个「人不会主动去开」的位置上**：面板头号按钮（评审）
   在没钉住评分模型时点下去 462ms 返回 409（实测 profile `eto-selftest` 与插件默认配置都是这个状态）；
   而它唯一能持久化的那条路径（完整流程）全生命周期只写过 1 条记录。
2. **真正值得留的只有一件事：一个免费的、与云端不同源的第二意见**。实测本机 `qwen3-8b-arb`
   在 57 秒里给出三条实质疑虑（量化指标缺失、技术债、云端/本地一致性），前两条计入结论、
   第三条被解析器丢掉但原文可读 —— 三条我写提案时都没想到。
   其余 5 个工具要么模型自己做得更好（route / clarify / review），要么前提不存在（file lock / 单 agent）。
3. **所以改法不是加功能，是换触发点和换承载面**：工具面从 7 个收到 2 个（schema 4127→1860 字符），
   触发从「想起来打开面板」改成「删除/部署/合并前自动跑」，面板从输入框改成只读台账。

## 一、它该解决谁的什么问题

先回答一个更前的判断：**现在它的判断有没有价值？** 有，但只在一种形态下有 —— 见下面的场景 1。

下面三个场景都满足「DSH 用户每天会遇到 + 现在替代做法确实不够 + 成功可观测」。

### 场景 1：合并或宣布「做完了」之前，要一份不同源的复核

- **触发时机**：对话里。当任务进入「准备合并 / 准备交付」时，模型按工具描述里的触发条件自己调
  `eto_consensus`（不是人想起来去开面板）。
- **今天的替代做法**：① 同一个模型自审 —— **相关性太高**，它写的东西它自己审不出来；
  ② CI —— 只管机械正确性（能不能跑、测试过不过），不管方案取舍；③ 派 subagent 复核 —— 用的是同一个后端模型，
  同一套盲区。
- **为什么 ETO 能改善**：`eto/stitches/consensus/vote.py` 换掉的不是「再想一遍」，是**三套 system prompt × 一个不同权重的本地模型**。
  实测证据（本 ticket 现场跑，`docs/demo` 里是逐字原文）：
  - researcher 0.75：「未明确量化效果评估指标和长期维护策略」
  - coder 0.65：「存在一定的技术债务风险，特别是在模型质量保障和长期维护方面」
  - auditor（未计入结论，被解析器丢掉）：「未考虑云端模型和本地模型的切换风险及数据一致性问题」
  - 三条针对的都是我自己写的改造提案，而我写的时候一条都没想到。**这正是「不同源」的价值 —— 不是更聪明，是盲区不同。**
- **可观测成功标准**：一周内 `eto_consensus` 被调用 ≥3 次；其中 ≥1 次的某条 concern 被**采纳并改了东西**
  （台账里给每条记录一个「有用」标记，weekly 汇总）。

### 场景 2：不可逆操作之前，三个角度先泼一次冷水

- **触发时机**：对话里，命中触发词（删除 / 部署 / 迁移 / 批量替换 / 改认证）时自动。
- **今天的替代做法**：模型自己会提醒风险 —— 但它是**一个**视角，而且是同一个采样分布。
  本机 8B 的 auditor prompt 专盯「最坏情况会怎样、什么预防措施没考虑」。
- **可观测成功标准**：这类操作前有评审记录的比例。这是**过程指标**，不是质量指标 —— 别把它当门禁，
  它只值一次额外意见（见第五节「风险」）。

### 场景 3：主模型不可用时的兜底判断

- **触发时机**：云端 provider 限流 / 403 / 额度耗尽时。
- **今天的替代做法**：**没有**。会话直接卡住或降级成「随便给个答案」。
- **为什么 ETO 能改善**：`eto_consensus` 固定走本机 Ollama（`vote.py:13`，`ETO_OLLAMA_MODEL` 默认 `qwen3-8b-arb:latest`），
  与云端额度完全解耦；`eto_peer_score` 反过来跟随会话模型 —— 两者互补，一个挂了另一个还在。
- **可观测成功标准**：在 provider 报错的那一轮会话里，仍拿到了一份结构化评审（`status` + 每 peer 的 concern）。

### 明确砍掉的「伪场景」

| 曾经想做 | 为什么不成立 |
|:--|:--|
| 「不确定任务类型时用 route」 | 实测 10 条日常任务 7 条落到同一个兜底 `knowledge/direct/0.7`，连「修 /api/run 的超时」都判成 knowledge。它和「今天天气怎么样」给同一个答案。 |
| 「派活前用 clarify 自查」 | 是关键词表（命中「弄一下」「优化」）。模型自己判断更细，且我们已经知道要写文件/行号/验收标准。 |
| 「跨会话共享记忆」 | 作为通用 KV 它比不过「写个文件 + grep」。全库 44 个 key，**44 个都是机器写的，没有一条是人的备忘**（31 条 workflow + 12 条 eto + 1 条 learn，key 名全是 `wf_*` / `peer_score:*` / `smoke:*` 这类）。留作台账存储即可。 |
| 「多 agent 文件锁」 | 单 agent 环境下没有第二方来抢锁。`~/.eto/file_states/` 自 11-05 起是空目录。 |
| 「让 ETO 派活给 peer 执行（agent_execute）」 | 与 subagent 重复，且更弱（无工具、无沙箱、无审查）。 |

## 二、面板的正确形态

**结论：面板不该是工作台，该是台账。人会打开它只有一个理由 —— 查过去，不是发起未来。**

证据链（三条，互相独立）：

1. **它现在的主按钮开箱不可用**。在真实 DSH 实例（profile `eto-selftest`，与桌面版共用同一个
   `dsh-eto` 插件）点「评审」，462ms 返回 `panel scoring needs peerScoreProvider and peerScoreModel in the ETO settings page`。
   原因在 `lib/index.js:316-320`：面板是裸 HTTP handler，没有 `exec.agent`，拿不到会话路由，
   只能读设置里钉住的 `peerScoreProvider/Model`；而 `~/.dsh/profiles/*/cordis.patch.yml` 里一个都没配
   （对全部 profile 逐个 grep `peerScore`，零命中）。
   > 口径说明：桌面 profile 的 `[settings]` 存在 DSH 的配置存储里，不在 `cordis.patch.yml`，
   > 所以「桌面版也一定没配」这一点我**没有直接证据**；有直接证据的是 `eto-selftest` 这份配置。
   > 但同一个 409 分支对两者都成立：它只在设置被显式钉住时才放行。

2. **它写下的东西没人读**。面板输入框 → 结果落 `localStorage`（会话一滚就没）；
   唯一进共享记忆的路径是「完整流程」写 `flow:last`（`lib/client.js:560`），而**全仓没有任何读取方**，
   且这条路径全生命周期只写过 1 条（11-05 14:31）。
   面板里用于写记忆的 UI（`wbMemory*` 文案、`client.js:94-96`）已随记忆区一起从面板撤掉，
   只剩「完整流程」这一个隐式写入点。
3. **它和对话是两个世界**。浏览器半区拿不到 host 的 `agents`，所以「导入到对话」必然失败（已在 PR #46 删除）。
   现在只能「复制 JSON」手动粘 —— 也就是说：**面板里得出的判断，要人肉搬运才进得了对话。**
   一个需要人肉搬运的判断，等于没有被采纳。

所以形态定为：

| 维度 | 现在 | 改成 |
|:--|:--|:--|
| 入口 | 侧栏图标 → 输入框 + 4 个按钮 | 侧栏图标 → **只读列表**（按时间倒序，可按状态筛） |
| 发起评审 | 在面板里点按钮 | **在对话里**（工具调用），触发条件写进工具描述 |
| 结果落地 | localStorage | `~/.eto/reviews/<ts>.json` + 工具卡片（对话里直接可见） |
| 面板职责 | 发起 + 展示 + 历史 | **只做两件事**：翻历史、看某条为什么降级 |
| 输入框 | 有 | **删除**（它诱使人以为该从这里开始） |

一句话：**发起交给对话，留档交给面板。** 面板里唯一不可被对话替代的能力是「上周那个方案后来怎么评的」。

> 不做的事：不显示伪造的阶段进度（ETO 在 `peer_review` 返回前不吐任何阶段信息），
> 不加「导入到对话」（已确认不可行），不在面板里再做一个聊天框。

## 三、保留 / 降级 / 砍掉

依据只有一条：**DSH 自己做不到、或做起来明显更差的，才留。**

### 保留（2 个工具）

| 工具 | 为什么留 | 改什么 |
|:--|:--|:--|
| `eto_consensus` | 唯一的「不同源 + 免费 + 可留档」判断。三个 peer 三套 prompt，本机跑，不烧云端额度 | ① 描述里写清触发条件（删除/部署/合并前、云端不可用时）② 渲染第一行必须是「基于 2/3 个 peer」这种诚实口径 ③ 结果落台账 |
| `eto_peer_score` | 跟随会话模型，不依赖 Ollama —— `eto_consensus` 的反向兜底 | 保留，描述里说明「这是轻量版，一个视角」 |

### 降级（不出现在模型工具面，但保留代码）

| 项 | 降级成什么 | 理由 |
|:--|:--|:--|
| `eto_memory_write/read` | 内部存储层（台账 + 共识写回） | 44 个 key **全部**机器自写，没有一条人类备忘 —— 这说明「记住 XXX」这个用法事实上从未发生。模型要记东西应该写文件；「记一下」由台账覆盖 |
| `eto_peer_config` | 设置页只读 | 它是配置文件的无参数读取器，模型没有理由调 |
| `eto_clarify` | 可留作内部预检（不注册为工具） | 关键词表，模型自己更准；但作为「派活前的机械自查」无害且快（评估报告实测 29ms） |
| `eto_route` | 从工具面拿掉 | 7/10 兜底。除非先修成非兜底判断，否则留着只是让工具面变贵 |

### 砍掉

| 项 | 理由（带证据） |
|:--|:--|
| `eto_file_status/update/release` | 单 agent 环境无第二方抢锁；`~/.eto/file_states/` 自 11-05 起为空目录 |
| `agent_execute` | 与 subagent 重复且更弱；且它的历史记录是「24/31 失败、7 条 ok 里含 provider error」 |
| `eto_review` | 只是给一段 JSON 写摘要，模型自己读完就有 |
| `eto_feedback` | 写 `routing:constraints`，只有 `mcp_dispatch.dispatch_with_spec` 会注入，而插件不走那条路径 |
| 面板输入框 + 4 个按钮 | 见第二节 |
| 面板「完整流程」 | 它写出的 `flow:last` 无读取方，且路由那一段是错的（11-05 那条把「把 MCP 桥改成插件」判成 knowledge/direct） |

**工具面的直接收益（实测，不是估算）**：把 `lib/tools.js` 的 `createTools()` 结果序列化
（`name + description + parameters + output.schema`）量长度：

| 组合 | 字符数 |
|:--|--:|
| 当前 `enabledTools` 7 个 | **4127** |
| `eto_consensus` + `eto_peer_score` | **1860**（−55%） |

复跑方式：把 `lib/{tools,spawn,config}.js` 复制到任意有 `@deepseek-ai/*` 的目录，
`node --input-type=module -e "import {createTools} from './lib/tools.js'; …JSON.stringify…"`。

## 四、实现方案（三步）

### 第一步：换触发点 + 收窄工具面（≤1 小时，有可观测结果）

| 项 | 内容 |
|:--|:--|
| 改哪个文件 | `packages/dsh-eto/cordis.patch.yml`（`enabledTools` 7 → 2）、`packages/dsh-eto/lib/tools.js`（`eto_consensus` 的 description 与 render） |
| 改动量 | 约 40 行（白名单 5 行 + 描述 15 行 + render 12 行 + 测试 1 条） |
| 验证方法 | ① 重启 DSH，`GET /@dsh-eto/api/status` 的 `registered` 从 7 变 2（本轮已实测该字段会如实反映：`eto-selftest` 配了 2 个，接口就返回 `["eto_consensus","eto_route"]`）② 单测断言 degraded 结果的第一行渲染文本 ③ `node --test tests/` 全过 |

那句话在 `actions` 数组里，要往下读进 JSON 才看见。上一轮评估（issue #43）判断过：
「退化」的信息在语义里，不在传输里，所以工具层没有任何理由报错。

## 五、这次实测发现的两个新问题（不在 issue 已知事实里）

### 5.1 「部分掉队」仍然会让结论看起来比实际可信

现场实跑（`eto_consensus`，2026-11-06 19:18，56.9s）返回：

```json
{"status":"approved","final_score":0.75,
 "votes":[{"peer":"researcher","score":0.75}, {"peer":"coder","score":0.65},
          {"peer":"auditor","score":null,"provider_error":true}],
 "degraded":true,"degraded_peers":["auditor"],
 "actions":["1/3 个 peer 无有效评分（auditor），结论仅基于其余 2 个"]}
```

`degraded: true` 有了（PR #46 的功劳），但 `status` 依然是 `approved` —— 因为 `vote.py:316`
只按「可用 peer 的平均分」判。读者第一眼看到的是 `approved`，那句「只基于 2/3」在 `actions` 里。
**建议**：`degraded` 时 `status` 加后缀（`approved_partial`）或把 `degraded_peers` 提到渲染第一行。
这是渲染层可以单独修的事，不必动判定逻辑。

### 5.2 1/3 的评审被一个格式问题吃掉，而且它是间歇的

同一份提案里 auditor 掉队，原因是回复中「第一段完整 JSON + 后面的 `</think>` + 第二段半截 JSON」
被 `_extract_json`（`vote.py:202-211`，取第一个 `{` 到最后一个 `}`）拼成一个非法 JSON。
**它真实给出的疑虑是「未考虑云端和本地模型的切换风险及数据一致性问题」—— 这条被整段丢掉了。**

为了判断这是「必挂」还是「偶发」，我把同一个 prompt 连打 7 次（3 个 peer 轮换）：

```
researcher ok / coder ok / auditor ok / auditor ok / researcher ok / coder ok / auditor ok
PARSE_FAIL_RATE 0 / 7
```

**7 次全过** —— 所以这是个**间歇**故障，不是设计缺陷。含义有两层：

- 好消息：不用重写解析器；
- 坏消息：它不可预测，而它每次都吃掉 1/3 的评审。**这就是「评审看起来还行，但总少一个声音」的根因。**

候选修法（都很小，任选其一或叠加）：① `_extract_json` 改成「扫描所有平衡的大括号块，取最后一个能解析的」；
② `_call_ollama` 加 `"think": false`（本机实测对 qwen3 有效，但不保证每次）；
③ 解析失败时**重试一次**（当前直接放弃）。

顺带发现同一文件里两处同类静默：`vote.py:340`（T2 审议解析失败 → 沿用旧分）、
`vote.py:352`（T3 终审解析失败 → 静默保留原 status）。它们不影响主结论，但失败无痕。

### 5.3 关于评估报告里排第 1 的 `workflow.py:166`

`docs/eto-assessment-2026-11.md` §五 把「修 `workflow.py:166` 与 `protocol.py:53`」列为优先级 1。
我核对了一遍可达性：`_success_rate` 只被 `select_agent` 调用，`select_agent` 只被
`bidding/workflow.py` 的 `generate_steps` 与测试调用，而**这个插件没有暴露 bidding/workflow 的任何入口**
（`lib/eto_runner.py` 的 `HANDLERS` 里没有，`eto/mcp_server.py` 的 13 个工具里也没有）。
所以对「日常会用到的插件」而言，它的影响面接近 0 —— 该修，但**不该排在改造方案的第一位**。
本方案的排序是：先解决「没人用」，再解决「用起来的边角失真」。

顺手把它跑出来，确认「静默降级」在这个函数上的实际形状（本机现状）：

```
_success_rate('coder') = 0.5        # 因为 get_outcomes('coder') 返回 []（0 条 task_outcome）
select_agent("写一个登录页", [...]) -> 'c'
```

也就是说：**共享记忆里明明有 31 条 workflow_step 的失败记录，`_success_rate` 一条都看不到**
（`get_outcomes` 只认 `type == "task_outcome"`，而那个类型全库只有 1 条），于是每个 agent
的历史成功率恒等于 0.5 —— 「按历史成功率选 agent」这件事目前**没有历史**。

### 5.4 超时预算与真实耗时对不上

第二次实跑（19:23）76.2s，其中 coder 与 auditor 都报 `TimeoutError: timed out` ——
`vote.py:87` 的 `urlopen(timeout=30)` 是**单次调用**预算，而 8B 模型在 40K 上下文下响应常超过 30s；
peer 又是串行（`vote.py:289` 的列表推导）。结果是**越慢的 peer 越容易被判成「掉队」**，
而它可能只是答得更久。建议：单次预算抬到 60–90s，或 peer 并发（三个 peer 之间无依赖）。

## 七、风险与不做什么

| 风险 | 说明 | 对策 |
|:--|:--|:--|
| 本地 8B 判断质量有限 | 它给的疑虑是「值得考虑的视角」，不是权威结论。实测 r2 那条「直接合并到 main、不跑测试」拿到 `revise / 0.50` 而不是 `reject` —— 它指出了问题，但没给出与该问题相称的严重程度 | **只当额外意见，不当门禁**；台账里保留每个 peer 的原文供人判断 |
| 收窄到 2 个工具后插件显得单薄 | 这是取舍不是缺陷 | 用台账填满面板，而不是用工具填满上下文 |
| 触发靠模型自觉 | 描述写进 schema ≠ 一定触发 | 第三步用 10 条固定 prompt 量触发率；不够就改成「用户说合并时先跑」的显式约定 |
| 单次 30s 超时会把慢 peer 判成掉队 | 见 5.4 | 抬预算或并发 |
| 「有用」标记靠人点 | 不点就没有采纳率数据 | 可接受：宁可没有数据，也不要伪造一个采纳率 |

**不要做**（继承 `docs/eto-assessment-2026-11.md` 的清单，本次实测后新增两条）：

- 不重做「导入到对话」（浏览器拿不到 host `agents`）
- 不为省额度再拉一套云端推理栈（本机 qwen3-8b 已验证可用且免费）
- 不做工具按 preset 完全隔离（7→2 之后约 1860 字符 schema，收益不抵复杂度；596 tokens 是评估报告对 7 个旧工具的估计，本次未重测 token）
- 不给面板造假进度条
- **（新增）不把 `eto_route` 继续留在工具面上** —— 除非先把它从 keyword 兜底改成真判断
- **（新增）不把评审结果当成发布门禁** —— 它是一次额外意见，不是 CI
